Deterministic Jev

Jev turns text into typed decisions for software. Ask it the same question twice and it can answer differently. Deterministic Jev is an open server that speaks the same API and gives the same answer every time.

Same question, fifteen calls

We took the insurance claim from TypeSafe's own consistency cookbook and asked “is this claim covered?” fifteen times. Every request was byte-for-byte identical.

A guard you cannot retry past

A guardrail decides whether a message reaches your model. We ran TypeSafe's guardrail cookbook unchanged on 2,236 messages from four public safety test sets. Each message was sent byte for byte 10 times to hosted Jev and 5 times to Deterministic Jev.

Consistent is not the same as right. Our model lets TypeSafe's own “Neurosemantical Inversitis” jailbreak through every time. Hosted Jev catches it but switches between review and block from call to call. A miss that repeats can at least be caught by a test and fixed. Guardrail results in full →

Why a decision should repeat

Replay it

When a claim is routed wrongly, rerun the logged request and get the same number. You debug the input, not the noise.

Test it like code

A snapshot test can assert the exact probability. No tolerance bands, no flaky reruns, and any model or prompt change shows up as a diff.

Audit it later

A reviewer can re-derive a moderation, lending or claims decision months later from the log and a fingerprint.

Every claim, with the run behind it

Measured on 2026-09-28 with Bespoke-Nimble-9B on SGLang 0.5.19, one H100 NVL.

Guardrail suite

TypeSafe's “Guardrails for LLMs” battery (four hazard questions and a severity score) and its strict routing, applied to XSTest, ToxicChat, in-the-wild jailbreaks and JailbreakBench behaviors. A message counts as flagged when it is not passed. Hosted Jev got 10 identical calls per message, the local servers 5, all at up to 32 concurrent requests.

“Leaks on some calls” counts unsafe messages that were passed on at least one call and stopped on another. For those, resending the same text is enough to get through. Latency is the median for one guard call at a time on our H100; hosted Jev latency is not compared.

Labels come from each dataset. ToxicChat marks toxic content broadly, so every guard's recall on it is low. Hosted Jev is a different, larger model, and these differences in detection are specific to this suite and this policy.

What “the same answer” means here

Default serving usually picks the same option. The probabilities under it wobble, and a threshold near the wobble eventually gets crossed. Below is one real request from the test set, sent 30 times to each server. Every distinct float64 that came back is listed with its bit pattern.

TypeSafe's own consistency test, replayed

We sent TypeSafe's exact cookbook request (one auto-insurance claim, 14 yes/no questions, 15 calls in a row) to our server. Their protocol adds a fresh random uid to the state on every call, so their spread mixes run-to-run noise with sensitivity to that field. We ran it both ways.

On byte-identical requests, default serving produced a mean per-question spread of and flipped fraud_flag between yes and no on a busy GPU. Deterministic Jev's spread was exactly zero. With the uid protocol our spread () is close to Jev's published 0.0102, and fraud_flag still flips. Determinism freezes the output for a given input. It does not make the model ignore a field it should ignore.

Nothing else moved

Batch-invariant kernels change the arithmetic, so we reran the full 324-request held-out set from Nimble's release with determinism on and off. Every decision matched.

These runs used the first build. The final build reproduces all 324 answers bit for bit (see Receipts). Bespoke reports 90.1% for the original Nimble checkpoint and 93.2% for Jev 1.13 on this set. The current checkpoint, served at its default temperature of 1.0, scores 87.0% on both of our servers. Our goal is determinism, not a better model.

What it costs

On fresh requests, determinism costs almost nothing on this workload. A Jev call is one short prefill and a single token read, so the batch-invariant kernels barely register. Every level below uses requests the server has not seen, with the cache flushed first.

The upstream flow sends a separate warm-up call before each question, which costs a round trip. Deterministic Jev skips it when there is only one question, and that accounts for the gap with default serving. With the same flow, the two servers are within a millisecond and within 1% of each other.

Determinism does give up one thing. The patch only keeps exact state checkpoints, so the engine can no longer reuse part of a cached prompt when the exact same request comes back. Because answers are a pure function of the request bytes, the server can instead memoize whole responses, which is not safe on a nondeterministic server. With --memo, exact repeats return in 61 ms at 344 decisions per second. An earlier benchmark that replayed the same requests at every level had shown default serving at 111 decisions per second, and that figure came from exactly this kind of cache reuse.

What determinism does not fix

Bit-for-bit reproducibility applies to identical bytes. We sent each of the 324 held-out requests in variants that mean the same thing and counted decision flips.

Key order inside state changed 19 decisions, because the model reads the serialized JSON. Our --canonicalize option sorts keys before prompting, and that brings it to zero. Option order and a nuisance uid are changes to content the model sees. Fixing those takes training or symmetrized prompting, which is on the roadmap below.

How it works

From a deterministic flag to a deterministic answer

A decision you can replay

TypeSafe built Jev as a fast decision function for software. You give it a state and typed questions, and it returns probabilities instead of a generated paragraph.

“Think of Jev as a frontier-intelligence function call: unstructured state in, typed probabilistic decisions out.”typesafe.ai · Introducing System One Models and Jev

Their pitch is software-like reliability: calibrated probabilities, answers that always match the schema, and “smart if-statements” inside ordinary code paths. An if-statement has one more property that engineers take for granted. Run it twice on the same input and it takes the same branch. TypeSafe measured this for Jev and says so directly:

“This policy does not make the model deterministic.”docs.typesafe.ai · consistency cookbooks

In their insurance-claim cookbook, the covered question returned between 0.43 and 0.53 across 15 calls, on both sides of a 0.5 threshold. That is fine for a demo and awkward for claims processing, snapshot tests or an audit trail. Deterministic Jev closes that gap for self-hosted serving. For a fixed deployment, identical request bytes give identical probability bits.

Why the deterministic flag was not enough

SGLang ships --enable-deterministic-inference, which swaps in batch-invariant kernels so a request's numbers do not depend on what else is in the batch. We checked it at the engine level, reading the label log-probabilities a Jev server consumes, with up to 64 background tenants mixing prefill and decode.

The flag works on the plain transformer. On the hybrid model it left 22 of 300 repeats drifting, and neither of the obvious knobs (the triton backend, aligned prefill splits) removed it. A pair probe narrowed it down. Batching the target with any companion was harmless (56 of 56 identical). All 8 failures in 84 cases were requests that resumed from their own cached prefix of 100, 152, 200 or 252 tokens. A resume at 64 tokens was exact.

The fix has three parts. A ten-line SGLang patch keeps deterministic mode from saving a state checkpoint unless the prefill ends exactly on the 64-token grid, where the state is the exact fp32 final state. A second small patch aligns chunked-prefill splits to the same grid, so a long prompt split under load resumes on a boundary too. Without it, a build that prefilled whole requests in one pass drifted on 20 of 720 repeats. Our server then trims the shared-state warm-up for multi-question requests to a multiple of 64 tokens, so every question branch resumes from an exact checkpoint. After the fix: 300 of 300 at the engine level, 84 of 84 in the pair probe, and 720 of 720 through the API.

Receipts

Every response carries an x-detjev-fingerprint header, a hash of everything that can change the bits: weight files, prompt compiler, SGLang version and numeric flags, GPU model and temperature. Same fingerprint and same request bytes give the same answer. We recorded all 324 held-out decisions as a golden file with the first build, then replayed it. The final build answers single-question requests in one pass instead of resuming from a cached warm-up, and it still matches the recorded file bit for bit.

The repository

  
One open repository that others can run, extend and cite: a deterministic Jev-compatible server, a replay test kit that works against any System One backend including hosted Jev, and a growing set of use-case suites with published result cards.

  

    
PartWhat it holds

    
      
server/Deterministic Jev: the /v1/systemone API, fingerprint header, canonicalization, exact response memo, decision receipts

      
patches/Engine patches, each with a regression test and its upstream status

      
replaykit/Backend-agnostic tests: identical-bytes replay, drift under load, restart and cross-GPU golden files, invariance, retry attack

      
tasks/One folder per use case: a card (why it must repeat, source, license), an adapter to Jev requests, gold labels, metrics

      
results/Versioned result cards keyed by backend and fingerprint, with the raw JSON behind every number

      
spec/The determinism contract: what goes into a fingerprint, the receipt format, canonicalization rules, so any server can claim and prove compliance

    
  

  
Every result card reports the same columns: accuracy, calibration (Brier, ECE), replay rate, decision flips on identical bytes, retry-attack pass rate, invariance flips, latency and cost. Contributors can add a task, a backend, a model or an engine fix. CPU tests run on every pull request, and GPU replay runs attach their fingerprint and raw output.

Where this creates value

  
TypeSafe positions System One as the fast layer of software automation: routing, triage, moderation, guards and verification, called from ordinary code. Each of those gets something concrete from a replayable decision.

  

    
NeedWhat determinism gives it

    
      
Debugging a bad route or triageReplay the logged request and get the same probability, so the investigation is about the input, not sampler noise.

      
Tests for smart if-statementsSnapshot tests assert exact probabilities with no tolerance bands and no flaky reruns. A prompt or model change shows up as an exact diff.

      
Audit and regulated decisionsClaims, lending, moderation appeals: a reviewer can re-derive the exact score from logged state and fingerprint.

      
Map-reduce over large datahash(request, fingerprint) is a correct cache key, so jobs can dedupe inputs and resume after a crash without drift.

      
A/B tests and migrationsDifferences between arms come from the change being tested, not from 0.01-level jitter. No need for 15 repeats per condition.

      
Agent loopsTool choice, escalation and routing take the same branch on replay, so agent failures reproduce.

      
Privacy and controlSelf-hosted on one GPU: state never leaves the building, and no rate limit or alias changes without notice.
